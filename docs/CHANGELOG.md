## v3.10.0 · 后台自动分析 · 相册监听 · 检索隔离

**解决的问题**：分析要能在后台常驻运行、自动发现并分析新照片，且不能影响前端搜索。

- `AnalysisService` 改为 `START_STICKY` 常驻守护，跑完不退出；新增 `MediaStoreObserver`
  （ContentObserver + 1.5s 防抖）监听相册，`BootReceiver` 开机/升级恢复，App 回到前台兜底拉起。
- 相册变化 → 重新查 MediaStore → `AnalysisPlanner.diff/plan` 只挑新增照片 → 逐张落盘保存；
  新照片立即显示在相册里，AI 描述与 EXIF 随后自动补齐。
- **三层隔离**保证搜索不受影响：分析跑低优先级独立线程；服务只写自己的磁盘 Store，
  不碰前端检索快照；结果按批增量通知前端，只 `invalidate` 新增的几张文档缓存，
  **绝不全量 `clear()` + 全库重算**（删除旧版 `syncServiceResults()` 路径）。
- 设置页 / 首页菜单 / 通知栏均可停止守护；关闭后回到 v3.9.0 一次性分析 + 前台续跑模式。
- 详细架构、系统限制与降级见 [BACKGROUND_ANALYSIS.md](BACKGROUND_ANALYSIS.md)，
  完整变更见 [CHANGELOG_v3.10.0.md](CHANGELOG_v3.10.0.md)；离线评测 `BackgroundEval` 46/46 PASS。

## v3.9.0 · 断点续分析 · 版本说明与操作手册

**解决的问题**：照片多的时候，每次分析都会中断，下次又要从头重新分析。

根因是旧实现用「上次已分析张数」当相册列表下标续跑，且要求照片总数完全一致：照片数一变（新增/删除/扫描波动）就 `clear()` 删掉全部结果；`isComplete` 后再点分析也走 `startIndex = 0`；再加上每 200 张才落盘一次、进程被强杀时走不到保存逻辑，几万张照片几乎永远跑不完。

**改动**：

- 新增 `AnalysisPlanner`（纯 Kotlin，可离线评测）：按 **photoId 差集** 计算待分析队列，已落盘的绝不重跑；支持照片增删、排序变化、重复 ID 去重。
- 落盘粒度降到**单张**：`AnalysisResultStore.appendResult()` 每分析完一张立即追加一行 JSONL；meta 计数按间隔刷新；恢复时以行文件里的 ID 为唯一权威。
- 中断兜底：`finally` 与 `Service.onDestroy()` 都写入「未完成」标记；`START_NOT_STICKY`，改由应用回到前台时自动续跑（可在设置里关闭）。
- 云端 AI 描述缺失的占位结果，下次开启 AI 时自动补齐；连续失败 20 次本轮自动降级为本地分析，不再逐张退避拖慢几万张照片。
- 首页状态条改为「已分析 X 张，还有 Y 张待分析」；分析中显示「还剩 Z 张（可随时退出，下次自动继续）」。
- 批量重分析与单张重分析改用 `appendResults(ids, ...)`，不再对几万条缓存做全表扫描。
- 新增应用内「版本说明」`AboutScreen` 与「操作手册」`HelpScreen`（可折叠、可搜索），设置页版本号改为动态读取。
- 新增 `docs/USER_MANUAL.md`、`docs/RESUME_ANALYSIS.md`、`tools/ResumeEval.kt`。

**验证**：`ResumeEval` 35/35 PASS；v3.8.0 `PerfEval` 26/26、v3.7.0 `V37Eval` 41/41、v3.6.0 `ExifSearchEval` 25/25（F1=1.000）、v3.5.2 `RecallEval` 0.933 全部保持。

## 升级与降级

- **覆盖安装**：直接安装新版 APK，已分析结果、EXIF 缓存、手动标注地点都会保留。
- **回退版本**：安装旧版 APK 同样可覆盖；若提示签名不一致，先卸载再安装。
- **数据清除**：卸载应用会清除全部私有数据。分析结果保存在 `filesDir`，不随 APK 迁移。
- **签名密钥**：所有版本必须使用同一 keystore 签名；`PhotoSearch-release.jks` 不可提交到公开仓库。
