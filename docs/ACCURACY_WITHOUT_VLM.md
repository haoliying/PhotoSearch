# 不依赖大模型，如何提高照片识别准确度（v3.11.0）

> 本文回答一个具体问题：**关掉云端大模型之后，「有汽车的照片」这类搜索为什么不准，以及不换模型能怎么修。**
> 适用版本：v3.11.0（versionCode 14）。应用内「操作手册」有对应的操作指引。

---

## 一、先定位：不准的原因不在「模型不够大」

项目一直有两套识别能力：

| 通道 | 实现 | 是否联网 | 产出 |
| --- | --- | --- | --- |
| 端侧识别 | ML Kit Image Labeling / Object Detection / Face Detection | 否，纯本地 | 英文标签 + 置信度、物体框、人脸、主色、场景 |
| 云端大模型 | VisionLanguageAnalyzer（智谱 / 通义 / 硅基流动，OpenAI 兼容格式） | 是 | 中文描述 + 8~20 个中文关键词 |

关掉大模型后只剩端侧通道。但过去端侧通道**算出来的信息大部分没被用上**，检索层还额外设了几道过严的门槛。逐条对照：

| # | 根因 | 代码位置（v3.10.0） | 后果 |
| --- | --- | --- | --- |
| 1 | **主色算了但只存不用** | `EnhancedImageAnalyzer.analyzeColors()` 返回 5 个量化色，`ConceptRegistry.buildSearchIndex()` 完全没读 `dominantColors` | 「蓝天」「雪景」「黑白」「暖色调」等一切颜色/氛围查询都搜不到 |
| 2 | **构图信息完全没进索引** | `width / height` 只用于详情页展示 | 「竖幅」「横幅」「全景」「长图」搜不到 |
| 3 | **人数信息被压缩成布尔** | `toSearchableTags()` 里 `faces.isNotEmpty()` 只加「有人/微笑」 | 「单人」「双人」「合影」「人群」区分不了 |
| 4 | **`hasText` 权重低于命中阈值** | `buildSearchIndex()` 给 `hasText` 0.50 权重，而 `TEXT_MIN_EVIDENCE = 0.55` | 端侧明明检测到文字，搜「截图 / 文档」却永远 0 结果 |
| 5 | **低置信标签整体丢弃** | `labels.filter { confidence >= 0.30f }` | 远景小车、遮挡宠物、局部物体常常只有 0.15~0.30 的置信度，直接被扔掉 —— 这是「有汽车的照片」漏召的主因 |
| 6 | **只保留得分最高的一个场景** | `classifyScene()` 返回单个 `SceneType` | 一张「夜晚 + 城市 + 车」只留一个标签，另外两个概念全部丢失 |
| 7 | **查询侧没有同义词** | `IntentParser` 的 `keywords` 只有用户原词 | 端侧标签 `Vehicle` 翻译成中文是「车辆 / 交通工具」，用户搜「汽车」，全文索引里根本没有「汽车」这个词，概念通道又受置信度门槛限制 → 漏召 |
| 8 | **单条证据一票否决** | `evaluateCondition()` 只要没有任何一条证据 ≥ 0.55 就判不命中 | 三条 0.50 的弱证据明明互相印证，仍被判为「不相关」 |

也就是说：**主要损失发生在「信号 → 索引 → 查询」这段链路上，而不是图像模型本身。** 在不换模型、不联网、不重跑分析的前提下，这一段能修回很大一部分。

## 二、方案总览：四条不改模型的改进路线

v3.11.0 的本地增强（`LocalVisualTags` + `QueryExpander` + `SearchEngine` 新增通路）落在四条路线上：

| 路线 | 做什么 | 解决上面的根因 | 代价 |
| --- | --- | --- | --- |
| **A. 把已有信号全部编入索引** | 主色、亮度、饱和度、宽高比、人脸数、`hasText`、EXIF 推断 → 中文可检索标签 | 1 / 2 / 3 / 4 | 零额外计算（部分字段升级后补采） |
| **B. 降低证据损失** | 多场景标签、0.15~0.30 低置信标签以弱权重入索引 | 5 / 6 | 索引条目略增 |
| **C. 查询侧同义扩展** | 「汽车 → 车辆 / 轿车 / vehicle / car …」，按概念组隔离，命中分打折 | 7 | 每查询最多 32 个扩展词 |
| **D. 多弱证据叠加** | 单条弱证据不命中；2~5 条相关弱证据按递减系数累加后可命中 | 8 | 仅原词全不命中时才触发 |

**关键设计：全部是纯函数，输入是已经落盘的结构化字段。** 因此：

- **升级即生效**：历史分析结果不需要重跑，打开新版立刻享受增强；
- **完全离线**：不联网、不消耗大模型额度、不上传照片；
- **可回退**：设置页一个开关即可关闭，关闭后检索行为与 v3.10.0 逐字节一致；
- **可验证**：`tools/V311Eval.kt` 63 项断言，含 3 万张照片性能。

## 三、逐项实现

### A. 本地视觉信号 → 中文标签（`LocalVisualTags`）

从 `PhotoMetadata` 已有的字段推导，按确定性分三档权重（与 `TEXT_MIN_EVIDENCE = 0.55` 对齐）：

| 档位 | 权重 | 标签类型 | 能否单独命中 |
| --- | --- | --- | --- |
| `W_CONCRETE` | 0.66 | 竖幅 / 横幅 / 方形 / 全景、单人 / 双人 / 合影 / 人群、文字 / 文档、黑白、竖长图+文字→手机截图 | 是 |
| `W_STRONG` | 0.60 | 主色调、蓝天 / 绿植 / 暖色调、夜景 / 暗光、多场景中文词、鲜艳 | 是（排序靠后） |
| `W_WEAK` | 0.44 | 次要颜色、低置信标签、截图 / 招牌 / 票据等具体载体、EXIF 推断 | 否，需叠加 |

细节：

- **颜色**：`dominantColors` 是量化 RGB，纯 Kotlin 位运算还原 r/g/b；蓝色占比高且亮度中高 → `蓝天 / 晴朗`；绿色 → `绿植 / 草地`；暖色 → `暖色调 / 秋色`；高亮低饱和 → `雪白`。
- **亮度 / 饱和度**：新版分析时一次采样顺带算出 `brightness / saturation` 落盘；**旧缓存没有这两个字段时，从 `dominantColors` 兜底估算**，所以老照片一样能搜「夜景」「黑白」。
- **构图**：`ratio = w/h`，≥2.2 判全景/长图、≥1.25 横幅、≥0.80 方形、否则竖幅；竖长图（ratio ≤ 0.62）叠加 `hasText` 才给「手机截图」强权重 —— 避免把普通竖幅人像误标成截图。
- **人数**：`faceCount`（旧数据回退 `faces.size`）→ 单人 / 双人 / 合影 / 人群；单人竖幅额外给「自拍」。
- **文字**：`文字 / 文档 / 含文字` 给强权重；`截图 / 招牌 / 票据` 等**具体载体只给弱权重**。这一区分很重要：早期版本把 `hasText` 直接提为「截图」强证据，导致「有文字的书页照片」被「截图」召回，精确率从 1.00 掉到 0.50，评测发现后已修正。

### B. 多场景 + 低置信标签

- `EnhancedImageAnalyzer.classifyScene()` 改为 `scoreScenes()` 返回**全部**场景得分，`multiSceneTags()` 把所有得分 ≥ 2 的场景翻成中文标签写入 `sceneTags`。一张夜景城市车照现在同时有「夜景 / 城市 / 车辆 / 汽车」。
- 0.15~0.30 置信度的标签不再丢弃，英文原文与中文翻译一起以 0.44 弱权重入索引。远景小车常只有 `Vehicle: 0.22`，现在能被检索到。

### C. 查询同义扩展（`QueryExpander`）

词表按**概念组**隔离，不做链式扩散（不会出现「汽车 → 车轮 → 火车」）：

```
汽车 → 轿车 / 小汽车 / 机动车 / 车辆 / 卡车 / 公交车 / car / vehicle / sedan …
```

约束：

1. 只对**已归一到规范概念**的查询条件启用扩展；词表外的自由词（咖啡、笔记本电脑）不扩展，避免把同类但不同的物体混在一起。
2. 中英文交错保留：端侧标签原文是英文，`vehicle / car` 往往比中文同义词更直接命中。
3. 扩展词是**兜底通路**：先走概念通道，再走原词全文，都不命中才尝试扩展词；且要求证据 ≥ 0.62（比原词 0.55 更严），命中分打 0.85 折，排序低于直接命中。
4. 组粒度刻意收紧：自行车 / 摩托车不与汽车同组；跑步不与游泳同组；「截图」不与「文字 / 文档」同组。

### D. 多弱证据叠加（`SearchEngine.evaluateCondition`）

```text
原词路径：与 v3.10.0 完全一致，第一个达到 0.55 的证据即返回
（保证历史语义零回归）

新增路径（仅 localEnhance = true 时）：
  收集所有 > 0 的证据分数并降序
  若 ≥ 2 条：agg = top1 + Σ(topi × (0.30, 0.24, 0.18, 0.12))
  agg ≥ 0.55 → 命中，source = "text:multi(N)"
  否则尝试扩展词（≥ 0.62，命中分 ×0.85）
```

效果是「三条互相印证的弱线索」可以顶替「一条强线索」，而单条弱证据仍不会误召。

### E. 顺带修复：后台对账死循环

旧版后台守护的 `while` 循环里，若云端 AI 持续失败，已分析但描述为空的照片会被 `plan()` 反复排进队列，形成原地无限重试、持续消耗 API。v3.11.0 增加「上一轮待处理集合」比对：同一批照片连续两轮待处理且期间无新增照片时退出本轮循环，交给相册变化或用户下次手动触发。

## 四、效果验证

`tools/V311Eval.kt`（Kotlin 1.9.22 真实编译 + JVM 运行）**63 / 63 通过**，关键项：

| 断言 | 结果 |
| --- | --- |
| 关闭增强时检索语义与 v3.10.0 完全一致 | 通过（G1 / G4 / G6 / G10） |
| 开启增强后，低置信 `Vehicle` 车辆照片被「汽车」召回 | 通过（G2，关闭时为 0 条） |
| 「截图」能召回竖长图文字照片，不误召回书页照片 | 通过（G5 / G11） |
| 「竖幅」能召回竖幅照片 | 通过（G7） |
| 旧格式分析结果（无新增字段）无需重跑即得到增强标签 | 通过（E1~E5） |
| 3 万张照片冷检索 | 372 ms（缓存命中 267 ms） |

历史 7 套评测全绿，其中召回评测 `MACRO_F1` 由 0.911 提升到 **0.933**（`截图` 精确率回到 1.00）：

## 五、边界、取舍与进一步可选方案

**这一版刻意没有做的事**，以及原因：

| 可选方案 | 能带来什么 | 为什么这版没做 |
| --- | --- | --- |
| 端侧 OCR（ML Kit Text Recognition 中文包） | 截图、文档、菜单、车票、聊天记录里**具体文字**可搜 | 需要新增约数 MB 模型依赖、增大 APK 与构建风险；本版先用「文字/文档/截图」分类标签覆盖，已预留 `ocrText` 字段与索引通路，接入 OCR 只需在 `EnhancedImageAnalyzer` 里填充该字段 |
| 端侧 TFLite 分类模型（MobileNet / EfficientNet-Lite） | 比 ML Kit 通用标签更细的物体类别 | 需要下载并打包模型文件、增加推理耗时；几万张照片下会明显拉长首次分析 |
| 相似照片标签传播（连拍聚类） | 同一场景连拍中，把清晰照片的标签传给模糊照片 | 需要跨照片的全局索引与聚类，会破坏当前「单张文档缓存 + 增量失效」的检索隔离模型，得不偿失 |
| 用户反馈闭环（点「不相关」降权） | 个性化准确度 | 需要标注 UI 与持久化反馈数据，属独立功能 |

**结论**：在本地信号被充分利用、查询扩展和弱证据叠加补齐之后，端侧通道的召回短板已明显改善；剩下的差距主要来自「通用图像分类模型本身的类别粒度」，那才是需要换模型才能解决的 part。因此 v3.11.0 同时提供 `UNCERTAIN` 策略 —— **把有限的大模型额度只花在端侧识别不确定的照片上**，两种通道互补，而不是二选一。

## 六、给用户的配置建议

| 你的情况 | 建议配置 |
| --- | --- |
| 完全不想联网 / 没有 API Key | 策略选「不使用大模型」，保持「启用本地准确度增强」开启。升级后旧结果无需重跑 |
| 想省流量但尽量准 | 策略选「仅识别不确定的照片（推荐）」，阈值 55%，并开「仅 Wi-Fi 下使用大模型」 |
| 只想精修少数几张 | 策略选「仅手动选择的照片」，在相册里多选 → 点「用大模型分析所选」 |
| 存量照片已有描述，只想处理新拍的 | 策略选「仅新增 / 未分析的照片」 |
| 想对比增强效果 | 设置页关掉「启用本地准确度增强」，保存后检索行为回到 v3.10.0 |
